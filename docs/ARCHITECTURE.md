# ChessWar Architecture

이 문서는 ChessWar 프로젝트의 설계 원칙과 시스템 경계를 정의하는 절대적인 기술 청사진이다.  
구체적인 설계 의사결정 이력과 기술적 타협의 근거는 [ADR.md](ADR.md)에 기록한다.

---

## 1. Architecture Identity

이 프로젝트의 핵심 아키텍처는 **"`Component` 패턴을 적용한 OOP 및 DOD 철학을 차용한 `Hot-Path` 최적화"이다.**  
마인크래프트 엔진 위에서 확장성과 서버 `Tick` 성능을 확보하기 위해 다음 철학을 기조로 삼는다.

1. **Rich Domain Model**: 일반적인 비즈니스 로직은 철저한 객체 지향을 따른다. 상속의 한계를 극복하기 위해 조립형 `Component` 패턴을 채택하며, 데이터와 로직을 완벽히 캡슐화해야 한다.
2. **DOD-inspired Optimizations**: 집중적으로 호출되는 `Hot-Path`에 한해서만 객체 지향의 캡슐화를 제한적으로 포기하고, 데이터 지향 설계 철학을 차용하여 연산 성능을 극대화한다.

---

## 2. Object Roles

프로젝트를 구성하는 핵심 객체들은 엔진 의존성 유무와 시스템 내 책임 범위에 따라 명칭이 엄격하게 통제된다.

### 2.1. Entity
논리적인 ID 식별 및 `Component`를 묶어두는 컨테이너 객체이다. `Entity` 자체에 비즈니스 로직을 구현하는 것은 허용되지 않으며, 오직 부착된 `Component`의 생명주기를 관리하고 전파하는 역할만 수행해야 한다.

### 2.2. Component
특정 기능에 대한 데이터와 그 데이터를 조작하는 고유 비즈니스 로직을 함께 캡슐화하여 소유한다. 외부에서 `Component`의 데이터를 임의로 조작하는 것을 금지하며, `Component`가 스스로 상태를 변경할 수 있도록 행동 메서드를 제공해야 한다.

### 2.3. Manager
`Component`의 데이터를 외부에서 가져와 독점 연산하는 `God Object` 및 `Anti-Pattern` 생성을 엄격히 금지한다. 개별 `Entity`의 내부 로직에 개입하지 않으며, 전역 상태 통제와 `Feature` 간의 굵직한 이벤트 조율만을 전담한다.

### 2.4. Processor
단순한 비즈니스 로직 조율이나 생명주기 관리 목적으로 `Processor` 명칭을 사용하는 것은 허용되지 않는다. 이 명칭은 오직 `Hot-Path` 내부에서 다량의 원시 데이터를 일괄 연산하는 집중형 객체에만 부여해야 한다.

### 2.5. Input Controller
클릭, 상호작용 같은 엔진의 외부 이벤트를 수신하여 순수 도메인 데이터로 변환한 뒤, 내부 시뮬레이션 영역으로 전달하는 진입점이다.

### 2.6. View
시뮬레이션 상태 갱신이 완전히 끝난 후 데이터를 단방향으로 읽어들여 파티클, 사운드, 블록 패킷 등 클라이언트 시청각 연출만을 전담한다.

## 3. Execution Path Strategy

마인크래프트 서버의 방어를 위해, 실행 경로의 성격에 따라 최적화 기법을 이원화하여 적용한다.

### 3.1. Cold-Path
유저의 클릭, 턴 전환, 피격 등 `Tick`마다 반복되지 않고 간헐적으로 발생하는 로직이다.
*   **원칙**: 철저한 가독성, 유지보수성, 불변성 확보.
*   **규칙**: 새로운 객체 할당 허용. 섣부른 최적화는 가독성을 해치므로, `GC`가 처리할 수 있는 영역은 철저히 객체 지향적으로 작성.

### 3.2. Hot-Path
이동, 충돌 판정, 파티클 연산 등 메인 `Tick`이나 `PlayerMoveEvent` 같은 고빈도 이벤트에 의해 초당 수십 번 이상 집중 호출되는 로직이다.
*   **원칙**: 힙 메모리 할당 방어 및 CPU 캐시 지역성 확보.
*   **규칙**:
    1. **Object Pooling**: 새로운 객체 할당 절대 금지.
    2. **In-place Mutation**: 새로운 객체 반환 대신 기존 객체의 내부 필드 직접 수정.
    3. **Primitive Arrays**: 래퍼 클래스 대신 원시 타입 배열 및 전용 컬렉션 강제.

## 4. Communication Rules

`Component` 및 `Feature` 간의 통신 시, 캡슐화 보존과 성능 사이의 딜레마를 해결하기 위한 규칙이다.

### 4.1. Read and Write Separation
*   타 `Feature`에서 내부 `Component`의 데이터 조회는 항상 허용.
*   타 `Feature`에서 내부 `Component`의 데이터 임의 변경은 접근 제어자를 통해 물리적으로 차단.

### 4.2. State Mutation Protocol
*   **Intra-Entity**: 동일한 `Entity`에 부착된 `Component` 간의 소통은 성능 최우선이므로, 객체 직접 참조 및 메서드 호출 허용.
*   **Inter-Entity**: 서로 다른 `Entity` 간의 통신은 유연성 최우선이므로, 직접 참조를 피하고 글로벌 이벤트 버스를 통한 느슨한 결합 지향. 단, 로직의 원자성 보장을 위해 이벤트 처리는 메인 스레드 상에서 동기적으로 즉시 완료.

### 4.3. Global State Transition
거대한 환경 셋업을 동반하는 전역 상태 전이는 반드시 `사전 검증 ➔ 환경 셋업 및 부수 효과 처리 ➔ 메인 상태 갱신 ➔ 이벤트 발행` 순서를 엄격히 따라야 한다. 상태를 먼저 갱신할 경우 타 로직이 셋업 도중에 개입하여 치명적인 좀비 상태를 유발할 수 있다.

## 5. Engine Boundary

플러그인 환경의 특수성으로 인한 엔진 종속성을 안전하게 격리하는 규칙이다.

### 5.1. First Class Objects
`Vector`, `UUID` 같은 순수 3D 수학 또는 식별자 객체는 래핑 오버헤드를 막기 위해 시뮬레이션 로직 내부로 적극 들여와 사용한다.

### 5.2. Heavy Engine Object Prohibition
`Player`, `World`, `Location`, `Block` 등 Bukkit 엔진이 생명주기를 관리하는 객체를 시뮬레이션 영역의 멤버 변수로 영구 저장하는 것은 절대 금지한다. 식별 및 좌표 저장이 필요하다면 `UUID`, `Vector` 같은 순수 원시 데이터로 변환하여 저장하고, 필요할 때만 엔진 API를 통해 조회해야 한다.

### 5.3. View Isolation
시청각 연출 API는 시뮬레이션 로직에 섞여서는 안 된다. 이는 철저하게 독립적인 `View` 모듈로 분리해야 하며, 데이터 흐름은 반드시 시뮬레이션 상태 갱신이 완전히 끝난 후 `View` 모듈로 단방향 전달되어야 한다.

## 6. Packaging Strategy

계층이나 기술적 역할 중심이 아닌, 게임의 특정 기능 묶음인 `Feature` 단위의 패키징을 사용한다.

### 6.1. Flat Packaging
새로운 `Feature`를 개발할 때, 패키지 내부에 `Entity`, `Component`, `Input Controller`, `View` 클래스를 모두 평탄하게 배치하는 것이 원칙이다.
*   **Encapsulation Defense**: 같은 패키지 내부에 위치시킴으로써 자바의 접근 제어자를 활용하여 타 `Feature`의 무분별한 상태 접근 차단.
*   **View Isolation**: `View`가 `Component`의 상태를 임의로 조작하지 못하도록, 읽기 전용 인터페이스를 추출하여 주입하거나 엄격한 코드 리뷰로 방어.

### 6.2. Boundary Split
단일 `Feature` 패키지의 클래스 수가 관리 임계치를 초과하면 하위 패키지로 분리한다. 분리 기준은 '순수 데이터 및 비즈니스 로직'과 '엔진 입출력 및 연출' 두 가지로만 나누어 엔진 의존성을 물리적으로 격리해야 한다.

---

## 7. The Priority Pyramid

원칙과 실제 개발 상황이 충돌하는 딜레마 상황에서는 아키텍처의 `Design Pillars`를 수호하기 위해 다음 우선순위를 기준으로 의사결정을 내린다.

1. **👑 1순위 MVP 생존**: 동작 가능한 최초 기능 구현 및 기획 검증이 항상 최우선이다.
2. **🥈 2순위 엔진 법칙**: 마인크래프트 서버 `Tick`을 방어하기 위한 `Hot-Path` 최적화는 객체 지향 캡슐화 원칙보다 우선한다.
3. **🥉 3순위 기획 기반 가독성**: 복잡한 아키텍처 패턴의 적용보다 기획서의 의도를 명확하게 투영하여 가독성을 높인 코드가 우수하다.
4. **🔨 4순위 구조적 패턴 준수**: 조립형 `Component` 분리나 디자인 패턴 규칙은 맹목적으로 강제하지 않는다.
