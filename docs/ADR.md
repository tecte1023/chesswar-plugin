# 📄 ChessWar Architecture Decision Records (ADR)

이 문서는 ChessWar 개발 과정에서 결정된 구체적인 기술적 선택,
핵심 게임 설계, 그리고 성능 최적화 의사결정 기록을 보관합니다.

## Architectural Background

본 프로젝트는 약 1년간의 개발 과정을 거치며 아키텍처의 근본적인 전환인 `Soft Reset`을 단행했습니다.

초기에는 엔터프라이즈 환경의 DDD 및 헥사고날 아키텍처를 채택하였으나,
Minecraft의 물리적 `Tick` 환경에서는 이러한 추상화가 한계에 부딪혔습니다.
Minecraft 서버의 20 TPS 한계를 방어하면서도 유지보수성을 확보하기 위해, 기획 중심의 GDD 용어를 수용하는 방향으로 구조를 전면 개편했습니다.
아래 기록들은 프로젝트 초기의 `Soft Reset` 과정 및 그 이후의 지속적인 개발 과정에서 수립된 핵심 아키텍처와 세부 구현 타협안의 근거들입니다.

### ADR-001: Component-Based OOP Adoption

### Decision

깊은 클래스 상속 구조를 배제하고 `CB-OOP` 패턴을 최종 채택합니다.
Java 환경에 맞추어 순수 ECS 대신 객체 참조와 ID 방식의 절충안을 취합니다.
클래스로 구현된 `Composite Entity`를 데이터 루트로 삼아 하위 `Component` 참조를 조립합니다.
이러한 구조 조립의 책임은 각 `Manager`가 전담합니다.
매 20 TPS 연산의 성능 최적화를 위해, `Component` 내부 상태 변경 시
`Zero-GC Driven Mutation` 원칙에 따라 필드를 직접 수정하는 `In-place Mutation` 방식을 사용하도록 설계합니다.
단, 데이터 구조체인 `Component`와 `Composite Entity` 내부에 게임 로직을 포함하는 것은 전면 금지되며,
상태 변경은 오직 `package-private` 접근 제어를 통해서만 가능합니다.
`CB-OOP`는 데이터의 정체성과 설계 사상은 ECS/DOD 원칙을 따르되, 메모리 관리와 조립에만 OOP 문법을 사용하는 실용적 하이브리드 아키텍처입니다.
객체의 정체성은 메모리 주소가 아닌 ID 값에 귀속되므로, 기획적 상태 변화 이벤트 발생 시
`Composite Entity`의 메모리 참조를 교체하더라도 ID가 유지되는 한 기획적 동일 개체는 완전히 보존됩니다.

### Rationale

다중 상속 불가 문제를 회피하면서도 유지보수성과 성능의 최적 균형을 낼 수 있는 가장 현실적인 모델입니다.
마인크래프트의 20 TPS 환경에서는 객체 매핑 오버헤드가 큰 엔터프라이즈급 추상화나,
메모리 연속성이 결여되어 Java의 힙 영역에서 CPU 캐시 히트 최적화의 이점을 누릴 수 없는 순수 ECS 아키텍처 모두 성능에 비효율적입니다.
가비지 컬렉션 부하를 최소화하면서 `CB-OOP`의 정합성을 지키기 위해 이 모델이 낙점되었습니다.
또한, 객체 불변성을 일부 포기하더라도 데이터와 로직의 완벽한 분리는 타협할 수 없으며,
제어 책임을 `Manager`가 전담하도록 강제하여 아키텍처의 직관성을 유지합니다.

### 🛑 Anti-Patterns & Past Failures

#### Case 1: Failure of DDD and Hexagonal Architecture Adoption and Soft Reset

* **Failed Attempt**: 프로젝트 초기 약 1년간 엔터프라이즈 환경의 DDD 및 헥사고날 아키텍처를 실제 도입하여 구현을 진행했습니다.
* **Why it Failed**:
  마인크래프트 물리 엔진의 `Tick` 스레드 내에서 동적으로 객체를 매핑하며 발생하는 오버헤드가 서버 성능과 생산성을 극도로 저하시켰고,
  결국 아키텍처 전환인 `Soft Reset`을 단행하게 되었습니다.

#### Case 2: Rejection of DOD and Pure ECS at the Design Stage

* **Failed Attempt**: 아키텍처 전환 검토 과정에서 데이터 지향 설계인 DOD 및 순수 ECS 구조의 전면 도입을 분석했습니다.
* **Why it Failed**:
  메모리 연속성이 보장되는 C++과 달리, Java 레퍼런스 객체는 힙 영역의 메모리 파편화 특성상 DOD가 약속하는 CPU 캐시 히트 최적화 이점을
  얻는 것이 불가능하여 설계 및 프로토타이핑 단계에서 기각되었습니다.

#### Case 3: Attempt to Allow Helper Methods for Internal State Mutation inside Components

* **Failed Attempt**: 캡슐화 보장 명목 하에 상태 갱신 헬퍼 메서드를 `Component` 내부에 허용하여 상태를 수정하려 했습니다.
* **Why it Failed**:
  `Component`가 묶음 갱신과 같은 기획상의 게임 룰을 소유하게 되어 정체성을 상실하고,
  결과적으로 `Feature` 전반에 결합된 만능 객체가 생성되는 부작용을 초래했습니다.

### ADR-002: Composite Entity Identifier Criteria

### Decision

`Composite Entity` 내부에 허용되는 데이터는 가변성의 법칙에 따라 다음 3가지로만 엄격히 제한됩니다.

1. **Primary Key**: 객체를 특정하는 절대 변하지 않는 유일무이한 단 1개의 식별자만 허용하며 다중 키 결합은 전면 금지합니다. 복수형 속성으로 검색이 필요하다면 `Manager` 내부에서 배열을 평탄화하여 인덱스로 룩업해야 합니다.
2. **Component**: 메인 틱 루프에서 값이 계속 변해야 하는 가변 상태 데이터입니다. 가비지 컬렉터를 피하기 위한 내부 덮어쓰기 기법을 위해 반드시 가변 객체 껍데기로 감싸서 배치해야 합니다.
3. **Inlined Component**: 생성부터 소멸까지 값이 절대 변하지 않는 불변 고정 속성입니다. 포인터 체이싱을 막고 하드웨어 친화적 최적화를 달성하기 위해 `Component` 껍데기를 씌우지 않고 루트에 직접 인라인화하는 것을 허용합니다.

### Rationale

식별자가 여러 개 존재할 수 있다는 다중 키 발상은 객체의 정체성을 붕괴시키는 안티 패턴입니다. 
식별자를 제외한 모든 데이터는 원칙적으로 `Component` 껍데기 안에 담겨야 하나, 힙 영역에 포인터가 흩어지는 자바의 한계를 극복하기 위해 가변성을 기준으로 타협합니다. 어차피 변하지 않아 런타임에 껍데기 자체를 통째로 갈아치울 일이 없는 불변 객체를 가변 껍데기로 한 번 더 감싸는 것은 불필요한 이중 간접 참조 오버헤드만 낳으므로 루트 인라인화를 허용합니다.

### 🛑 Anti-Patterns & Past Failures

#### Case 1: Multiple Identifiers and Flat Attributes (Overwritten Rule)

* **Failed Attempt**: 과거에는 5개 이하의 데이터를 모두 식별자로 간주하여 `Composite Entity` 최상단에 평탄화하여 선언하는 룰을 강제했습니다.
* **Why it Failed**: 진짜 키와 일반 불변 데이터를 혼동하여 아키텍처의 기준점이 모호해졌고, 사실상 `Component` 캡슐화를 우회하여 온갖 잡다한 필드를 루트에 노출시키는 면죄부로 악용되는 참사가 벌어졌습니다.

### ADR-003: State-Manager Decoupling and Reference Passing

### Decision

게임 로직과 상태를 철저히 분리하는 `State-Manager Decoupling` 원칙을 채택하여,
핵심 상태 객체인 `Composite Entity`와 `Component`는 순수 데이터 구조체로 격리합니다.
`Manager`는 자신의 제어 흐름 관리를 위한 상태 외에 자체적인 가변 상태를 가질 수 없으며,
오직 생성자를 통해 `Component` 등의 상태 구조체 참조를 주입받아 `final` 필드에 보관하고 논리적 주권만 행사해야 합니다.

### Rationale

객체 간 상호 역참조로 인한 순환 참조를 제거하여, 20 TPS 메인 스레드 `Tick` 루프에서 발생하는 상태 불일치 및 런타임 에러를 원천 차단합니다.
또한, 메서드 호출 시마다 파라미터로 일회성 상태를 전달하는 대신 생성자를 통해 `final` 참조를 주입받아 보관함으로써,
불필요한 파라미터 전달에 따른 가비지 생성을 차단하고 로직의 응집도를 극대화합니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**:
  `Component`가 `Manager`를 역참조하거나, `Component` 내부에 묶음 갱신 등 복잡한 게임 로직을 혼합했습니다.
  또한 함수형 프로그래밍을 오해하여 매 메서드마다 파라미터로 상태를 넘기려 했습니다.
* **Why it Failed**:
  상태 전이의 추적이 불가능해져 동시 수정 예외나 메모리 누수 버그로 이어졌고,
  매번 파라미터 전달을 강제하면서 메서드 시그니처가 비대하고 복잡해졌습니다.

### ADR-004: Instantiation and Static Factory Rules

### Decision

객체의 생성 방식은 객체의 역할이 아닌 **"생성 과정에 어떠한 형태의 로직이 개입하는가?"** 라는 단일 기준에 따라 결정합니다.

* **로직이 개입하는 경우 (정적 팩토리 강제)**:
  `Hot Path` 성능 방어를 위해 캐시를 조회하는 플라이웨이트 객체이거나, 내부 상태의 정합성 검증 등 생성 시
  데이터 대입 이상의 제어 로직이 필요한 객체는 퍼블릭 생성자를 `private`으로 제한하고 정적 팩토리 메서드 사용을 강제합니다.
* **로직이 배제된 경우 (정적 팩토리 배제)**:
  `Composite Entity`, `Component`처럼
  파라미터를 필드에 대입만 하는 순수 데이터 구조체는 복잡한 공간 연산 및 구조 조립을 모두 외부에서 완료한 후 파라미터로 주입받아야 하며
  불필요한 정적 팩토리 메서드를 배제하고 퍼블릭 생성자의 직접 호출을 허용합니다.
* **상태가 배제된 순수 연산 객체인 `System`의 경우**:
  순수 연산 기능만 수행하는 `System`은 `Zero-GC` 원칙에 따라 열거형이나 정적 싱글톤으로 구현하는 것을 강제합니다.
  단, 연산을 보조하는 매핑 및 공급 객체는 다중 게임 세션 환경의 유연성을 위해 일반 클래스로 설계하여 생성자를 통해 필요한 참조를 전달받습니다.

클래스 기반 데이터 구조체(`Composite Entity`, `Component`)에는 모든 필드를 외부에서 명시적으로 주입받는 전체 인자 생성자만 허용합니다.
일부 필드를 암묵적 기본값으로 채우는 부분 인자 생성자는 초기화 로직이 데이터 구조체 내부로 침투하는 행위이므로 전면 금지됩니다.

### Rationale

메모리 할당과 상태 초기화 로직을 완벽하게 분리하면서도, 팩토리 패턴의 맹목적인 남용을 막아 순수 데이터 결합 시의 투명성과 가독성을 극대화합니다.

### 🛑 Anti-Patterns & Past Failures

#### Case 1: Initialization Logic Inside Constructor

* **Failed Attempt**: 생성자 내부에서 기하학적 좌표 계산이나 상태 가공 로직을 직접 수행하여 할당하는 구조를 고려했습니다.
* **Why it Failed**:
  저장된 게임 세션 상태나 스냅샷을 메모리에 단순 복구하려 할 때, 생성자가 호출되는 순간 내부의 초기화 로직이 원치 않게 강제 재실행되어
  전달받은 복구 데이터를 오염시킬 위험성이 극도로 높았기에 설계 검토 단계에서 기각되었습니다.

#### Case 2: Self-Assembling Composite Entity Static Factory

* **Failed Attempt**:
  `Manager`의 결합도를 완화하기 위해,
  최상위 `Composite Entity`가 스스로 하위 구조의 위치를 계산하고 자율 조립하는 정적 팩토리 메서드를 내부에 갖추는 구조를 검토했습니다.
* **Why it Failed**:
  `Composite Entity`가 단순 데이터 루트를 넘어 생성 및 조립이라는 무거운 책임을 소유하게 됨으로써
  `CB-OOP` 및 `ECS` 사상의 데이터-로직 분리 대원칙을 훼손하고,
  테스트 및 직렬화 과정에서 잠재적인 정합성 오류를 유발할 우려가 높아 설계 단계에서 기각되었습니다.

#### Case 3: Partial Constructor Usage

* **Failed Attempt**: 클래스 기반 데이터 구조체에 일부 필드만 인자로 받고 나머지는 암묵적 기본값으로 채우는 부분 인자 생성자를 허용했습니다.
* **Why it Failed**:
  호출부에서 인자를 실수로 누락한 것인지, 의도적으로 기본값을 주입한 것인지 구별이 불가능해졌습니다.
  암묵적 초기화 로직이 데이터 구조체 내부로 침투하여 `Component`의 순수 데이터 구조체 역할이 훼손되었으며,
  컴파일 타임에 검출되지 않는 런타임 상태 누락 버그의 원인이 되었습니다.

### ADR-005: Lifecycle-Based State Wrapping and Delegation Rules

### Decision

가변 상태를 묶는 구조체인 `Composite Entity` 및 `Component`와, 생명주기가 긴 불변 데이터 구조체인 `Value Object`를 철저히 분리하며,
위임 허용 기준을 상반되게 적용합니다.

1. `Value Object`는 `Component` 내부의 필드로 참조되어 참조 홀더 역할을 수행하며,
   `Warm Data` 참조 교체 방식을 통해 가변 상태의 생명주기를 안전하게 관리합니다.
2. 가변 구조체인 `Composite Entity`와 `Component`는 내부 로직의 침투와 비대화를 막기 위해
   내부 구조를 은닉하는 **위임 메서드 작성을 전면 금지**하며, 제어 주체인 `Manager`에게 가변 필드를 직접 노출합니다.
3. 반면 불변 구조체인 `Value Object`는 외부 결합도를 낮추기 위해 **내부 자료구조를 은닉하는 위임 메서드 제공이 적극 권장**됩니다.
4. `Composite Entity`가 `Value Object`를 직접 필드로 소유하는 것은 금지됩니다.
   `Warm Data` 참조 교체의 방파제 역할을 담당할 `Component`를 반드시 경유해야 합니다.

### Rationale

상태 구조체는 제어 주체인 `Manager`가 실질적인 데이터인 불변 객체를 안전하게 획득 및 교체하게 해주는 참조 래퍼 역할에 집중해야 합니다.
가변 구조체가 위임 메서드를 소유하면 필연적으로 게임 로직을 내포하게 되어 `State-Manager Decoupling` 원칙이 붕괴됩니다.
반대로, 복잡한 공간 데이터 등을 담는 불변 `Value Object`는 내부 구조를 철저히 숨겨야 외부 객체들과의 과도한 결합을 막을 수 있습니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**:
  과거에는 캡슐화 원칙을 일괄 적용하여 `Composite Entity` 내부에도 수많은 위임 메서드를 만들었고,
  반대로 맵 데이터를 담는 불변 객체는 내부 자료구조인 리스트나 맵을 그대로 퍼블릭으로 노출했습니다.
* **Why it Failed**:
  `Composite Entity`는 각종 게임 규칙을 품어버리는 거대한 `God Object`로 변질되었고,
  반대로 데이터 구조체는 외부의 수많은 `Manager`들이 내부 자료구조에 직접 의존하게 되어, 맵 자료구조 변경 시 엄청난 연쇄 수정이 발생했습니다.
* **Failed Attempt**: `Composite Entity`가 `Value Object`를 직접 필드로 소유하도록 설계했습니다.
* **Why it Failed**: `Warm Data` 갱신 시 원자적 참조 교체를 담당할 `Component` 슬롯이 없어 `Composite Entity` 전체를 교체해야 했고,
  그 과정에서 다른 `Component`의 상태 누락이 발생했습니다.

### ADR-006: Strict Immutability of Warm/Cold Data

### Decision

데이터 생명주기에 따라 `Cold Data` 및 `Warm Data`의 갱신 전략을 `Hot Data`와 철저히 분리합니다.
매 `Tick`마다 갱신되지 않는 저빈도/중빈도 갱신 상태 구조체(예: `Component` 내부의 `Value Object` 상태, 맵 데이터 `Value Object` 등)는
객체 내부 필드의 직접적인 가변 조작이 전면 금지됩니다.
상태 갱신이 필요할 경우, 기존 객체의 필드를 비우거나 덮어쓰지 않고 완전히 새로운 인스턴스를 생성하여 참조를 원자적으로 교체합니다.

### Rationale

`Hot Data`가 아닌 이상, Java의 객체 할당 오버헤드는 20 TPS 방어에 큰 영향을 주지 않습니다.
오히려 기존 객체를 재사용하려다 필드 초기화가 누락될 때 발생하는 상태 누수 버그나 동시 수정 예외가 시스템 안정성에 훨씬 더 치명적입니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**:
  라운드 또는 턴 전환 시,
  기존의 거대한 상태 객체를 파괴하지 않고 재사용하며 내부 필드를 `clear` 메서드와 같은 초기화 헬퍼 메서드로 비워 사용했습니다.
* **Why it Failed**:
  단 하나의 필드라도 초기화가 누락되면 이전 게임의 낡은 상태가 새로운 세션에 잔존하여
  런타임 오류를 일으키는 치명적인 상태 누수 버그가 끝없이 양산되었습니다.

### ADR-007: Feature-Driven Packaging & Hybrid Sub-packaging Strategy

### Decision

`Feature-driven` 패키징을 유지하되, `Start Flat, Grow Deep` 철학 기반의 하이브리드 확장 전략을 채택합니다.

1. **Flat Initial Phase**:
   단일 `Feature` 설계 초기에는 패키지 격리보다 컴파일러 방어선 확보를 우선하며, 한 폴더에 모든 클래스를 모아 개발 속도를 극대화합니다.
   `I/O` 객체의 상태 조작 통제는 코드 리뷰 규약으로 방어합니다.
2. **Hybrid Expansion**:
   단일 `Feature` 내 구성 파일이 한계치를 넘어가는 디렉토리만 분할합니다.
   이때 `Entity`, `VO`, `Component`, `Manager` 등 핵심 코어부를 패키지에 고립시켜 `package-private` 방어벽을 구축하고,
   파일 개수가 팽창하는 `Input Controller`나 시각 연출 객체군을 하위 패키지로 물리적으로 밀어냅니다.

### Rationale

`Layer-driven` 패키징의 파편화 문제를 해결하기 위해 `Feature-driven` 패키징을 도입했습니다.
단일 `Feature` 내 구성 파일이 많아질 경우, Java 생태계의 특성상 하위 패키지로 분할하면
`package-private` 방어벽이 뚫려 상태 객체의 가변 메서드를 `public`으로 열어야 하는 캡슐화 붕괴 문제가 발생합니다.
따라서 초기 구조적 오버엔지니어링보다는 Minecraft 플러그인 생태계에 맞는 빠른 개발 속도를 우선시하여 `Start Flat` 구조를 유지합니다.
동시에 프로젝트가 거대해져 패키지를 분리해야 하는 시점이 오더라도 객체지향의 가장 중요한 원칙인 상태 캡슐화를 잃지 않도록
`Hybrid Expansion` 방어 구조를 내재화했습니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**: 캡슐화 방어를 위해 기능의 초기 설계부터 무조건 패키지를 철저히 분리하여 `I/O`를 강제 격리하는 방안을 검토했습니다.
* **Why it Failed**: 잦은 디렉토리 이동과 불필요한 보일러플레이트 코드를 유발하여 개발 생산성과 빠른 이터레이션을 심각하게 제한했습니다.

### ADR-008: Composition Root for Manager Systems

### Decision

1. **조립 6단계 순서 강제**: 진입점인 `Composition Root`에서 교차 의존성 꼬임을 막기 위해 `Infrastructure 👉 Component 👉 Presenter 👉 Manager 👉 Listener 👉 Registration`의 엄격한 6단계 순서로만 객체를 조립합니다.
2. **수평적 DI 금지와 데이터 직접 폴링**: `Manager`가 데이터를 얻기 위해 다른 `Manager`를 주입받아 함수를 호출하는 백엔드식 결합을 전면 금지합니다. 모든 로직 객체는 전역 데이터 배열 자체를 주입받아 독립적으로 폴링해야 합니다. 타 도메인 패키지에 데이터 참조가 공유되더라도, 상태 변경 헬퍼 메서드는 자바의 `package-private` 접근 제어자로 잠겨 있으므로 캡슐화가 완벽히 보장됩니다.
3. **전역 서브시스템 주입 예외**: 외부 물리 모듈 등은 의존성 주입 대상이 아니라 게임 엔진의 전역 컨텍스트입니다. `Composition Root`가 외부 모듈에 오염되는 추상화 누수를 막기 위해, 이들은 주입을 배제하고 `Presenter` 단에서 정적 호출로 자체 접근하는 것을 허용합니다.

### Rationale

`Manager` 간의 수평적 의존성 주입은 웹 백엔드의 서비스 레이어 결합 관성에 불과하며, 게임 엔진 아키텍처에서는 무의미한 강결합을 유발합니다. 데이터를 소유한 래퍼 객체만을 직접 주입받아 각자 폴링하는 것이 결합도를 최소화하는 정석입니다. 또한 렌더링 엔진과 같은 전역 서브시스템을 루트 조립 단계에서 주입하면 순수 게임 도메인이 외부 기술에 오염되므로 철저히 배제해야 합니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**: `Manager` 내부에서 다른 `Manager`를 직접 생성하여 자체적으로 조립하는 구조를 고려했습니다.
* **Why it Failed**: 제어 흐름의 추적이 어려워지고 상호 순환 참조로 인해 초기화 순서를 통제할 수 없게 되어 설계 단계에서 기각되었습니다.
* **Failed Attempt**: `BoardManager`가 `PieceManager`를 주입받아 데이터를 꺼내오는 수평적 의존성 주입을 시도했습니다.
* **Why it Failed**: `Manager` 간 강결합이 발생하여 로직이 서로를 알지 못해야 한다는 컴포넌트 기반 아키텍처의 철학이 붕괴되었습니다.

### ADR-009: Presentation-Game Logic Separation

### Decision

1. **엔진 데이터 객체의 실용적 허용:**
   Bukkit 엔진의 3D 공간 좌표 객체인 `Location`, `Vector` 등은 순수한 데이터 레코드로서,
   `Component`가 필드로 소유하거나 `Manager`가 틱 루프에서 직접 연산에 사용하는 것을 실용적으로 허용합니다.
2. **시각적 부수 효과의 엄격한 격리:**
   사운드 재생, 파티클 스폰, 스코어보드 갱신 등의 시청각 렌더링 부수 효과는
   게임 로직과 완벽히 격리하여 `Presenter` 인터페이스 뒤로 위임합니다.
   특히 스코어보드나 아이템 API 등 엔진 UI 객체를 원본 데이터로 삼는 것을 전면 금지하며,
   게임의 상태 데이터는 오직 핵심 `Feature` 내부 구조체에만 존재해야 합니다.
   상태가 변경된 후에는 상태 변경 이벤트를 통해 시각 정보를 일방향으로 동기화하는 것이 원칙입니다.
   또한 `Presenter`는 자신이 가진 시각화 상태 맵을 활용해 제어 주체인 `Manager`의 중복 실행을 몰래 수습해주는
   에러 은닉을 해서는 안 되며, 빠른 실패 가드 클로즈를 통해 즉시 `return` 처리하여 상태 무결성을 증명해야 합니다.
3. **로컬 피드백 호출 주체 분리와 트램프 데이터 방어:**
   상태 변이가 없는 단순 조회나 에러 알림 등 로컬 피드백 연출은 `Manager`를 거치지 않고 `Input Controller`가 직접 `Presenter`를 호출합니다.
   `Manager`는 예외 발생 시 렌더링 수단에 대한 어떠한 뷰 맥락도 인자로 넘겨받아서는 안 되며,
   오직 로직 검증 결과값만 반환하고 즉시 제어권을 돌려주어야 합니다.
4. **뷰 엔티티 생명주기 분리:**
   로비 버튼, 텍스트 등 시각적 인프라 역할을 하는 뷰 엔티티(`Interaction` 등)는 영구 속성을 비활성화하여 청크 복제 버그 및 월드 오염을 방지합니다. 반면, 전투 세션 중 복구가 필요한 핵심 게임 상태 엔티티만 영구 속성을 활성화하여 생명주기를 엄격히 이원화합니다.
5. **Dumb View Principle**:
   `Presenter` 내부에서 시각적 오프셋을 독자적으로 더하거나 빼는 것을 전면 금지합니다. 모든 기하학적 오프셋 연산은 `Manager`가 수행하여 최종 물리 좌표를 확정한 뒤 `Component`에 갱신해야 하며, `Presenter`는 이 좌표를 그대로 넘겨받아 맹목적으로 렌더링만 수행해야 합니다.

### Rationale

월드 좌표 변환 오버헤드를 막기 위해 단순 좌표 객체인 `Location`은 도메인에 허용하여 실용적인 `Tick` 성능을 확보합니다.
반대로, 무거운 엔진 시청각 API 호출은 `Presenter`로 격리하여 단호한 책임 분리를 달성하고,
풀링이나 비동기 처리 등 시각 연출의 복잡한 구현 방식이 코어 게임 로직을 오염시키지 않도록 방어합니다.
또한 `Presenter`가 에러를 은닉하면 게임 로직과 시각 연출의 상태가 어긋나는 데싱크 현상의 주범이 되므로 단호한 책임 분리가 필수적입니다.
여기에 더해, `Input Controller`가 받은 다양한 입력 소스의 맥락(명령어, GUI 클릭 등)을 렌더링 처리를 위해
억지로 `Manager`까지 밀어넣는 트램프 데이터 현상을 막아야 합니다.
뷰 렌더링을 결정짓는 컨텍스트가 코어 로직에 침투하는 결합도를 원천 차단하기 위해,
맥락을 처음부터 들고 있는 `Input Controller`가 로컬 렌더링 호출을 전담하도록 역할과 책임을 완벽히 분리합니다.

추가로, 어디에 렌더링할 것인지를 결정하는 오프셋 연산은 단순한 시각 효과가 아니라 게임 공간 내 엔티티의 절대적 물리 좌표를 획정 짓는 기획적 로직입니다. `Presenter`가 렌더링 시점에 임의로 오프셋을 더하게 되면 타 시스템이 의도적으로 조작하여 넘긴 정밀한 좌표를 뷰 계층이 훼손하게 됩니다. 최소 놀람의 원칙을 준수하기 위해 뷰 계층의 부수 효과 연산을 완벽히 차단해야 합니다.

### 🛑 Anti-Patterns & Past Failures

#### Case 1: Engine API Call within Main Logic

* **Failed Attempt**:
  전투 연산 공식 실행 도중 `playSound()` 호출이나 대량의 `spawnParticle()` API를 메인 스레드 게임 로직에서 직접 호출했습니다.
* **Why it Failed**:
  시청각 연출 코드가 핵심 게임 로직과 강결합되어 유지보수성이 박살 났으며, 이후 최적화를 위해 파티클 스폰 로직을 비동기 스레드로 분리하려 할 때
  핵심 전투 로직을 전부 뜯어고쳐야 하는 치명적인 아키텍처 경직성이 발생했습니다.

#### Case 2: Engine Item API as Source of Truth

* **Failed Attempt**: 타격 발생 시 엔진 아이템 API에서 수치를 읽거나, 피아 식별을 위해 스코어보드 팀 API를 매 `Tick`마다 호출했습니다.
* **Why it Failed**:
  시청각 연출 용도의 엔진 객체가 핵심 게임 데이터를 보관하게 되어 무결성이 훼손되었고,
  아이템 이동 등에 의해 객체가 파괴될 때 데이터가 증발하는 치명적인 생명주기 불일치 버그가 발생했습니다.

#### Case 3: Error Masking by Presenter

* **Failed Attempt**:
  `Presenter` 내부에 방어 코드를 짜서, 이미 켜져 있는 엔티티에 대해 다시 켜라는 명령이 오면 렌더러가 몰래 치워주고 재스폰하는 방식을 썼습니다.
* **Why it Failed**:
  겉보기엔 멱등성을 보장하는 듯 보이나, 실제로는 상태 제어 주체인 `Manager`의 생명주기 관리 실수를 숨겨주는 월권 행위로서
  대규모 상태 전환 시 랙과 버그를 유발하는 안티 패턴으로 전락했습니다.

#### Case 4: Tramp Data and View Logic Leakage into Manager

* **Failed Attempt**:
  `Input Controller`가 입력 이벤트를 받은 뒤,
  `Manager`의 헬퍼 메서드에 뷰 맥락 플래그를 넘겨주어(`trySkill(player, isGuiClick)`) 에러 출력을 맡겼습니다.
* **Why it Failed**:
  `Manager` 내부 로직에 특정 렌더링 방식을 결정짓는 뷰 분기문이 무분별하게 침투하여 코어가 뚱뚱해졌습니다.
  새로운 UI 입력 방식이 추가될 때마다 게임 룰과 무관한 코어 `Manager`를 뜯어고쳐야 하는 치명적인 개방-폐쇄 원칙 위반이 발생했습니다.

#### Case 5: Visual Offset Calculation by Presenter

* **Failed Attempt**: 로직 오염을 막겠다는 명분으로, `Manager`에서는 순수 바닥 좌표만 넘기고 `Presenter` 내부에서 렌더링 직전에 Y축 오프셋을 더하도록 설계했습니다.
* **Why it Failed**: 다른 구역의 로직에서 공중에 소환하기 위해 이미 계산된 Y축 좌표를 넘겼음에도 불구하고, 뷰 계층이 무조건 높이를 덧셈해버려 위치가 이중으로 왜곡되는 치명적인 데싱크 버그가 발생했습니다.

### ADR-010: Constant Placement — Game Balance Parameters vs Algorithmic Axioms

### Decision

코드베이스의 상수는 성격에 따라 두 가지로 분류하여 보관 위치를 결정합니다.

1. **기획 수치**:
   기획자가 게임 밸런싱을 목적으로 조정하는 수치는 `Value Object` 또는 열거형으로 격리합니다.
   `System` 로직 코드 내부에 리터럴로 선언하면 수치 변경 시 로직 코드 재컴파일이 강제됩니다.
2. **기하학 및 수학 공리**:
   체스판 규격에서 파생되는 이동 방향 벡터, 기물의 시작 열 등 알고리즘의 수학적 사실은 `System` 내부에 선언합니다.
   이는 밸런싱 대상이 아닌 알고리즘의 종류 그 자체이므로 `System`과의 응집도를 유지하는 것이 원칙입니다.

### Rationale

기획 수치와 알고리즘 공리를 구별하지 않고 `System` 내부에 혼재시키면, 밸런스 조정 시 로직 코드를 직접 수정해야 하는 상황이 발생합니다.
반대로 이동 벡터 같은 알고리즘의 불변 사실을 `Value Object`로 분리하면 연산 로직과의 응집도가 낮아집니다.
두 종류를 성격에 맞는 위치에 배치함으로써 게임 규칙 수정의 범위를 최소화합니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**: 기획 수치를 `System` 로직 코드 내부에 매직 리터럴로 직접 선언했습니다.
* **Why it Failed**:
  밸런스 수치 하나를 변경하기 위해 로직 코드를 직접 수정해야 했으며,
  동일한 수치가 여러 `System`에 분산 선언되어 한 곳에서 변경해도 나머지 위치가 누락되는 불일치 버그가 발생했습니다.

### ADR-011: Polling vs Event-Driven Communication

### Decision

게임 로직 실행 경로의 빈도와 제어 흐름의 성격에 따라 `Manager` 간 상호작용 및 소통 전략을 분리합니다.
지속 피해 등 매 `Tick`마다 갱신과 감시가 필요한 고빈도 로직은 `Manager`가 직접 상태 데이터를 조회하는
`Continuous Polling` 방식을 강제하며, 기물 파괴나 턴 종료 같은 비연속적인 상태 전이에 한해서만 가벼운 `Internal Event`를 발행하여
제어의 강결합을 해소하는 `Discrete Event-Driven` 방식을 허용합니다.

### Rationale

객체 간 결합도 완화라는 설계적 이점과,
매 `Tick`마다 발생하는 객체 생성 부하를 방어해야 하는 마인크래프트 20 TPS 서버 엔진의 물리적 제약 사이에서 타협하기 위함입니다.
`Continuous Polling`을 적용하면 이벤트 인스턴스의 힙 할당을 차단하여 `Zero-GC`를 유지할 수 있으며,
실행 빈도가 낮은 영역에 한해 이벤트를 허용함으로써 설계의 유연성을 확보합니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**:
  `Manager` 간의 상호 호출 결합도를 낮추기 위해 매 `Tick`마다 실행되는 갱신 및 감시 루프 전반에 걸쳐
  엔진 및 내부 이벤트를 발행하는 전면적 이벤트 주도 아키텍처 도입을 검토했습니다.
* **Why it Failed**:
  초당 수천 번 이상 발행되는 이벤트 객체의 생성 부하가 메인 `Tick` 스레드에 누적되어 힙 영역의 가비지 수집을 유발하고,
  주기적인 가비지 컬렉션 스파이크로 인해 `Tick` 레이트인 20 TPS 유지에 실패할 위험이 매우 높아 설계 단계에서 최종 기각되었습니다.

### ADR-012: Null Safety and Boundary Defense

### Decision

`Input Controller` 등 외부 엔진 입력을 받는 경계에서는 철저한 검증 및 `Early Return`을 수행하며,
이때 가독성보다 하드웨어 파이프라인을 배려한 `Ascending Cost Order` 원칙을 따라 가장 저렴한 연산(열거형 `==` 비교 등)부터 검증합니다.
게임의 모든 객체 영역(`Component`, `Manager`, `System` 등)에서는 `@NotNull` 어노테이션 기반의 정적 분석에 의존하여 런타임 체크를 생략합니다.
특히 `Hot Path` 내에서는 `if (val != null)` 형태의 검사 자체를 없애기 위해, 논리적으로 값이 없을 수 있는 데이터라도
`Warm Path` 단계에서 미리 활성 배열로 `Data Partitioning`을 수행하여 무지성 순회가 가능하도록 강제하며,
컬렉션 반환 시 `null` 대신 빈 배열(`new Type[0]`)을 반환하여 분기문을 완전히 제거합니다.
단, 불가능한 상태 방어는 원인에 따라 분리합니다. 내부 로직의 꼬임에 의한 불가능 상태(휴먼 에러)는 게임 루프의 폭발 반경이 격리된다는 엔진 특성을 활용하여 단언문(`Objects.requireNonNull`)으로 즉시 크래시를 내야 합니다. 반면, 외부 물리 엔진 요인에 의해 엔티티가 소멸한 경우에는 예외를 던지지 않고 조용히 조기 종료하여 우아한 성능 저하를 달성하는 것이 원칙입니다.

### Rationale

입력 검증 시 무거운 게임 객체 매핑 연산을 먼저 하면 CPU 사이클이 심각하게 낭비됩니다. 가장 싼 연산부터 쳐내어 `Fail-Fast`를 달성합니다.
또한 `Tick` 루프 깊은 곳에서의 런타임 널 체크나 빈 컬렉션 체크는 `Branch Prediction` 실패를 유발하는 오버헤드입니다.
데이터를 루프 진입 전에 완벽히 필터링하고 내부에서는 분기 없이 순회하는 `Branchless Execution`을 통해 오버헤드를 제거합니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**: 매번 코어 연산 루프 깊은 곳에서 런타임 예외 방어 코드를 수없이 작성하여 검증을 수행했습니다.
* **Why it Failed**:
  마인크래프트 서버 스레드는 자동 상태 롤백을 지원하지 않으므로, 예외 발생 시 메모리 내 게임 상태의 불일치가 불가피하게 발생합니다.
  결과적으로 매 `Tick`마다 무의미한 검사 지연과 분기 예측 실패가 누적되었습니다.

### ADR-013: Event-Based Custom Damage Control

### Decision

서버 엔진의 기본 데미지 이벤트를 최외곽에서 가로채어 강제 취소시키고,
독자적으로 계산된 커스텀 피해만을 대상 `Entity`에 원자적으로 적용합니다.

### Rationale

* **Why it Failed**:
  물리 엔진의 내부 연산이 완전히 차단되므로 세부적인 조건부 데미지 제어가 불가능해지고 타격 이펙트 연출 등에 한계가 발생했습니다.

### ADR-014: Effect and Ability Data Separation and Bitmask Architecture

### Decision

만료 기간이 있는 시한부 상태효과와 기물 고유의 영구 능력을 별도의 `Component`로 분리하여 관리합니다.
고유 능력과 시한부 효과 데이터는 처리 규칙이 근본적으로 다르므로 하나의 자료구조에 혼용하는 것을 전면 금지합니다.

상태효과 종류의 비트 인덱스는 단일 열거형으로 통합하여 개념 중복을 방지하되,
물리적 마스크는 영구 능력과 시한부 효과를 각각의 필드로 완전히 분리하여 보관합니다.
시한부 효과와 영구 능력의 데이터는 각각 `Flat Data Structure` 원칙에 따라 평탄화된 별도의 배열로 분리하여 보관합니다.
상태 객체를 깊게 중첩하는 구조는 원칙적으로 전면 금지합니다.

### Rationale

시한부 효과와 영구 능력을 하나의 자료구조에 혼용하면 순회 루프 안에서 종류를 판별하는 분기문이 강제되어 처리 비용이 상승합니다.
전체 해제 기믹 등 기획 규칙 추가 시 하드코딩된 예외 처리가 누적됩니다.
비트 인덱스를 단일 열거형으로 통합하면 양쪽에서 동일한 개념을 중복 정의하지 않아도 됩니다.
물리적 마스크를 이원화하면 각 `Manager`가 자신의 마스크만 읽어 독립적으로 처리할 수 있으므로 결합도가 최소화됩니다.
상태효과 데이터를 `Flat Data Structure`로 평탄화하면 `In-place Mutation`을 통해 새로운 객체 생성 없이 상태를 갱신할 수 있습니다.

### 🛑 Anti-Patterns & Past Failures

#### Case 1: Mixing Effect and Ability in a Single Array

* **Failed Attempt**: 시한부 효과와 영구 능력을 하나의 열거형 배열에 혼용하고 루프 내 분기문으로 처리했습니다.
* **Why it Failed**:
  전체 해제 기믹 발동 시 영구 능력까지 제거되는 것을 막기 위해 하드코딩된 예외 처리가 추가되었고,
  처리 규칙이 달라질 때마다 순회 로직 전체를 수정해야 하는 강결합이 발생했습니다.

#### Case 2: Splitting Status Types by Grade

* **Failed Attempt**: 동일 효과 종류를 등급별로 다른 열거형 값으로 분리하는 방식을 검토했습니다.
* **Why it Failed**:
  동일한 효과 종류의 인덱스 슬롯이 등급마다 달라져 중복 적용 방지와 덮어쓰기 로직이 지나치게 복잡해졌으며,
  `In-place Mutation`을 통한 효율적 갱신이 불가능했습니다.

#### Case 3: Index Partitioning in a Shared Interface Array

* **Failed Attempt**: 인터페이스 배열에 시한부 효과와 영구 능력을 함께 담고 인덱스 범위로 구분하는 파티셔닝 방식을 검토했습니다.
* **Why it Failed**:
  Java 배열은 데이터가 아닌 참조를 담으므로 메모리 연속성 이점이 없었습니다.
  두 종류의 데이터가 배열 내 인덱스 범위를 암묵적으로 공유해야 하는 강결합이 발생했으며, 다형성 처리 시 추가적인 타입 변환 비용이 발생했습니다.

### ADR-015: Semantic Immutability and Pre-calculation in Cold Path

### Decision

게임 기획상 절대 변하지 않는 물리적 실체는 `Cold Data`로 분류하며,
인스턴스 생성 시점에 모든 물리적 좌표와 오프셋을 완벽하게 사전 계산하여 불변 필드로 선언하고 영구히 고정합니다.

### Rationale

성능 최적화를 넘어 게임 모델의 의미론적 불변성을 코드로 입증하기 위함입니다.
초기화 시점에 좌표를 계산해두면 `Manager` 내부로 복잡한 분기 로직이 침투하는 것을 원천 차단하여 구조적 무결성을 극대화합니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**: 호출 빈도가 낮다는 이유로 연산이 필요한 시점마다 동적으로 좌표를 매번 재계산하도록 방치했습니다.
* **Why it Failed**:
  게임 규칙이 추가될 때마다 게임 로직 내부로 불필요한 좌표 계산 분기문들이 무분별하게 침투하여 개방-폐쇄 원칙을 위반했습니다.

### ADR-016: Stateless Strategy as System

### Decision

상태를 가지지 않는 순수 기하학 연산 객체나 전략 패턴을 비롯한 게임 규칙 검증 객체는 `System` 영역으로 완전히 분리하며,
정적 싱글톤 또는 열거형으로 구현하여 `Zero-GC` 원칙에 따라 힙 메모리 할당을 차단합니다.
이러한 객체들에는 `Manager` 접미사 사용이 엄격히 금지되며,
대신 연산 성격과 역할에 따라 `~Pattern`, `~Table`, `~Policy` 등의 명사형 복합어 접미사를 사용해야 합니다.

### Rationale

`Manager`는 게임 제어 흐름 관리에만 집중해야 합니다.
복잡한 탐색 연산이나 전략을 `Manager`가 내포하거나 해당 `Manager` 내부의 파편화된 객체로 취급하면,
무거운 연산 로직이 인스턴스화 오버헤드와 결합하여 `Tick` 성능을 저하시킵니다. 순수 연산은 상태 구조체로부터 분리되어야 합니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**:
  과거에는 다형성으로 분리된 순수 전략 패턴 객체들을 넓은 의미에서
  `Manager` 영역의 위임 객체인 `Delegate`로 취급하고 인스턴스화를 허용했습니다.
* **Why it Failed**:
  `Manager`라는 잘못된 위상 때문에 개발자들이 해당 전략 객체 내부에 무분별하게 가변 상태를 추가하는 부작용이 발생했습니다.
  결과적으로 매 `Tick`마다 무거운 연산 객체가 힙 영역에 대량으로 할당되어 GC 부하를 초래했습니다.

### ADR-017: Bunker System Adoption

### Decision

준비 단계에서 필요한 바닐라 엔티티를 보이지 않는 격리 구역에 미리 스폰해두고,
필요 시 텔레포트만으로 전장에 배치하는 `Bunker System`을 적용합니다.

### Rationale

서버 병목을 준비 시간으로 분산시켜 플레이어 경험을 쾌적하게 유지하기 위한 실전 최적화 기법입니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**: 전투 개시 시점에 마인크래프트 월드 내에 바닐라 엔티티 객체를 대량으로 실시간 스폰했습니다.
* **Why it Failed**:
  메인 `Tick` 스레드에 병목이 발생하여 플레이어가 가장 몰입해야 할 게임 시작 시점에 시각적 글리치 및 프레임 드랍이 발생했습니다.

### ADR-018: Terminology Split - Execution Path vs Data Lifecycle

### Decision

마인크래프트 서버 20 `TPS` 방어를 위한 두 개의 최적화 축을 협업 기준에 맞추어 명확히 분리합니다.

1. **실행 흐름**: 최적화 공학의 `Hot Path`와 `Cold Path` 개념을 차용하고, 이에 맞추어 `Warm Path`를 조합하여 정의합니다.
    - `Hot Path`: `Tick` 루프 내 고빈도로 실행되는 로직입니다.
    - `Warm Path`: 이벤트 등 간헐적으로 실행되는 로직입니다.
    - `Cold Path`: 부팅/종료 등 1회성으로 실행되는 로직입니다.
2. **데이터 생명주기**: DB/스토리지 산업 범용 용어인 `Data`를 차용합니다.
    - `Hot Data`:
      매 `Tick`마다 갱신되는 고빈도 데이터, 혹은 한 번에 대규모로 갱신되어 서버 지연을 유발할 수 있는 일괄 갱신 데이터입니다.
      가비지 스파이크를 막기 위해 불변성을 포기하고 `In-place Mutation`을 허용합니다.
    - `Warm Data`: 런타임 중 간헐적인 참조 교체가 일어나는 생명주기를 가지며, 갱신 시 객체를 통째로 새로 교체합니다.
    - `Cold Data`: 인스턴스 부팅부터 고정되어 세션이 끝날 때까지 영구적 불변으로 존재합니다.

### Rationale

기존 여러 문서에서 `Path`라는 용어가 실행 흐름 최적화와 데이터 생명주기 최적화 모두에 혼용되어 아키텍처적 인지 부조화가 발생했습니다.
용어를 명확하게 분리하고 정의함으로써, 코드의 실행 빈도와 메모리의 생명주기를 독립적으로 기술할 수 있습니다.
또한 1회성 실행 경로라도 대규모 할당이 한 `Tick` 내에 집중되면 가비지 컬렉터의 정지로 인해 서버 지연이 유발되므로,
실행 빈도뿐만 아니라 갱신 규모 기준을 `Hot Data` 분류에 포함시킵니다.
"`Grid` 클래스는 `Hot Path`에서 끊임없이 호출되지만 데이터 자체는 완벽한 불변이므로 `Cold Data`로 취급한다"
와 같이 모순 없이 아키텍처를 정의할 수 있게 됩니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**: 아키텍처 초기에 실행 흐름 최적화와 데이터 생명주기 최적화를 모두 `Path`라는 단일 용어로 혼용하여 표기했습니다.
* **Why it Failed**:
  "`Grid` 클래스는 `Hot Path`에서 끊임없이 호출되지만 데이터 자체는 완벽한 불변이므로 `Cold Data`로 취급한다"와 같은 상황에서,
  용어 혼용으로 인해 불변 객체를 어떻게 분류해야 하는지 아키텍처적 인지 부조화가 발생했습니다.

### ADR-019: Primitive Type and Scalar Pipeline Enforcement

### Decision

매 `Tick`마다 연산되는 `Component` 내부의 숫자 데이터나 공간 수학 계산을 담당하는 `Manager`와 `System` 영역에서는
래퍼 클래스 및 내부적으로 오토박싱을 유발하는 객체 사용을 금지하고, 반드시 `int`, `double` 등의 원시 타입 및 원시 타입 배열을 사용합니다.
또한, 1회성 연산을 위해 원시 데이터를 `Vector`나 `Double` 등 임시 래퍼 객체로 감싸는 래핑을 금지하고,
명시적으로 원시 타입 매개변수를 활용하는 `Scalar Replacement` 파이프라인을 유지합니다.

### Rationale

잦은 객체 인스턴스 할당으로 인한 `GC Pause` 현상을 원천적으로 방어하기 위해, 아키텍처 설계 영역에서 원시 타입 사용을 강제합니다.
`JIT` 컴파일러의 자동 최적화에 의존하지 않고, 메서드의 바이트코드가 길어지거나 스택 변수가 많아져 최적화가 배제되는 상황을 방지하기 위해
반드시 최적화가 수행될 수밖에 없는 원시 매개변수 파이프라인을 작성해야 예열 이전 단계의 연산 지연을 방지합니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**: `Tick` 루프 내부에서 숫자 연산 및 좌표 오프셋 처리를 위해 래퍼 클래스 객체를 무분별하게 할당하는 구조를 검토했습니다.
* **Why it Failed**:
  매 연산마다 임시 객체 생성 및 오토박싱/언박싱으로 인해 대량의 가비지가 생성되어
  `Tick` 레이트인 20 TPS 유지가 저해될 위험성이 설계 및 프로토타이핑 검토 중 발견되어 기각되었습니다.
* **Failed Attempt**:
  가독성을 우선하는 백엔드식 클린 코드 원칙을 맹목적으로 적용하여,
  로직을 다수의 작은 메서드로 쪼개고 연산마다 `Vector`와 같은 임시 래퍼 객체를 매개하는 설계를 기획했습니다.
* **Why it Failed**:
  `JVM` 기동 초기 및 매치 초반에 `JIT` 컴파일러가 예열되기 전인 인터프리터 모드 구간 동안 심각한 프레임 드랍과 예열 랙이 유발될 위험이
  개발 과정에서 발견되어, 원시 타입 기반의 `Scalar Replacement` 파이프라인으로 변경하여 선제 차단되었습니다.

### ADR-020: 1D Flattening and Zero-GC Pipeline in Hot Path

### Decision

`Hot Path`에서 실행되는 공간 탐색 로직에 대해 다음 최적화를 강제합니다.

1. 논리 격자 배열을 1차원 배열로 평탄화합니다.
2. 기물을 순회할 때 인덱스 기반의 `for` 루프를 사용하여,
   배열 인덱스 자체를 공간 오프셋 매개변수로 하위 파이프라인에 직접 전달하는 `Pipeline Feeding` 방식을 강제합니다.
3. 새로운 객체 인스턴스의 힙 할당을 차단하기 위해 기존 인스턴스에 `In-place Mutation`을 수행하는 패턴을 강제합니다.

### Rationale

1차원 배열 평탄화와 인덱스 매개변수 파이프라인을 구축하는 설계적 목적은 단순한 캐시 적중률 향상을 넘어,
탐색과 역추적 과정에서 발생하는 무의미한 래퍼 객체의 인스턴스 생성 루프를 원천 배제하여 가비지 컬렉터의 `GC Pause` 현상을 차단하기 위함입니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**:
  2차원 격자 혹은 해시맵 기반 탐색이나,
  기물 목록을 자바 컬렉션 프레임워크에 담아 순회한 후 다시 64칸 배열을 탐색하여 인덱스를 찾는 $O(n^2)$ 형태의 탐색 구조 도입을 검토했습니다.
* **Why it Failed**:
  탐색할 때마다 과도한 해시 연산과 임시 객체의 가비지 할당이 누적되어 `Tick Load`가 급증하고,
  이로 인해 20 TPS 유지가 불가능할 것으로 예측되어 설계 단계에서 평탄화 및 인덱스 파이프라인 구조로 전환하여 선제적으로 차단되었습니다.

### ADR-021: Path-Dependent Allocation Restriction

### Decision

성능 최적화와 개발 생산성의 실용적 타협을 위해,
힙 메모리 할당을 유발하는 순회 연산 및 스트림 처리의 사용 기준을 `Path`의 빈도에 따라 엄격히 이원화합니다.

1. **매 틱 실행되는 `Hot Path`**:
    - 람다 캡처링 및 스트림 파이프라인의 사용을 전면 금지합니다.
    - 가비지 생성을 차단하기 위해 컬렉션 순회 시 `Iterator`를 유발하는 문법을 절대 금지하며, 무조건 인덱스 기반의 순회만을 허용합니다.
    - 맵 객체의 순회를 지양하고 필요시 1차원 배열로 평탄화하여 접근합니다.
    - 단, 가비지를 유발하지 않는 원시 배열 및 일반 배열의 순회는 문법적 제약을 두지 않습니다.
2. **간헐적으로 실행되는 `Warm/Cold Path`**:
    - 가비지 컬렉션 부하가 미미하므로 개발 생산성과 가독성을 최우선으로 보장합니다.
    - `Iterator` 객체 할당을 유발하는 제네릭 컬렉션 및 맵 순회 문법의 사용을 적극 허용합니다.
    - 단, 언제든 로직이 `Hot Path`로 편입될 가능성을 염두에 두고 무분별한 스트림 파이프라인 남용은 여전히 지양합니다.

### Rationale

단순 반복 1회의 `Iterator` 할당은 가비지 컬렉터에 미치는 영향이 제로에 가깝습니다.
따라서 가비지를 유발하는 문법의 통제권은 데이터의 성질이 아닌 코드가 실행되는 빈도,
즉 `Path`에 전적으로 종속시킴으로써 성능 방어와 개발 편의성 사이의 완벽한 균형을 달성합니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**:
  과거에는 기획 변경에 따른 `Hot Path` 오염을 막기 위해 전역에서 보이지 않는 힙 메모리 할당을 무조건 강제 차단하는 정책을 고수했습니다.
* **Why it Failed**:
  간헐적으로 실행되는 `Warm/Cold Path`에서조차 복잡한 제네릭 컬렉션을 순회하기 위해 억지로 인덱스 기반 루프를 고집하게 되어,
  개발 생산성을 심각하게 저해하는 오버엔지니어링을 초래했습니다. 이에 따라 `Path`의 빈도에 따라 규칙을 이원화하는 것으로 정책을 수정했습니다.
* **Failed Attempt**:
  인게임 `Tick` 루프 및 실시간 이벤트 핸들러에서 가독성을 높이기 위해 스트림 파이프라인과 캡처링 람다를 활용하는 구조 설계를 검토했습니다.
* **Why it Failed**:
  람다 컨텍스트 캡처 및 스트림 파이프라인 처리 과정에서 발생하는 숨겨진 가비지 객체 할당이 `Tick` 루프에 누적되어
  서버 지연을 유발할 위험성이 개발 과정에서 발견되어, 전통적인 순회 방식을 유지하도록 선제적으로 차단되었습니다.

### ADR-022: Version-Based Lazy Evaluation

### Decision

전체 기물을 순회하는 방식이나 이벤트 리스너 기반의 반응형 갱신 방식을 폐기하고,
상태 갱신 시 글로벌 버전 인덱스 값만을 상수 시간으로 증가시키며,
탐색 시점에 버전을 비교하여 상태를 평가하는 `Lazy Evaluation` 구조를 채택합니다.
동일 원칙을 복합 스탯 연산에도 적용합니다. 합산된 최종 로직 스탯 수치를 객체 내부에 누적하여 미리 저장하는 것을 금지합니다.
대신 각 수치는 발생한 단위 `Component`가 별도로 보관하고, 전투 연산 등 조회가 발생하는 시점에만 `System`이 실시간으로 수집하여 계산합니다.
단, 클라이언트 화면 갱신을 위한 UI 이벤트 발송은 상태 변경 직후 즉각적으로 수행됩니다.
진영 전체에 적용되는 직업군 강화 수치는 개별 기물이 아닌 `game Feature`의 진영 단위 상태 관리 `Component`가 보관합니다.

### Rationale

실제 `Raycast` 연산을 플레이어가 조회하는 시점에만 자신의 버전과 비교하여 평가함으로써,
종속성 추적 오버헤드와 버그 발생 가능성을 완전히 배제하면서도 `Hot Path`를 완벽히 우회하는 최적의 설계입니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**:
  턴 전환 시점마다 영향을 받는 기물만 선별적으로 찾아가며 실시간으로 `Push` 방식의 즉각적인 조기 갱신을 수행하는 설계를 검토했습니다.
* **Why it Failed**:
  종속성 추적 분기가 극도로 복잡하여 단 하나의 조건이라도 누락되면 상태 불일치가 발생할 수 있고, 체스판에서 장애물이 비켜설 때
  탐색 범위 밖에 있던 아군이 갱신 대상에서 누락되는 `Unblocking Paradox` 버그 발생 가능성이 개발 단계에서 예견되어 최종 기각되었습니다.
* **Failed Attempt**:
  진영 전역 강화 발생 시 체스판 전체를 순회하여 해당 직업군 기물의 최종 스탯을 즉각 계산하여 기물 내부에 저장하는 방식을 검토했습니다.
* **Why it Failed**: 갱신 루프가 `Hot Path`에 편입되는 문제 외에도, 벙커 대기 중이거나 무적 상태인 기물이 갱신 대상에서 누락될 경우
  표기 수치와 실제 데미지가 일치하지 않는 상태 불일치 버그가 발생했습니다.

### ADR-023: Rejection of Magic Bitboard and Adoption of Hybrid Pathfinding

### Decision

일반적인 체스 엔진의 표준 아키텍처인 `Magic Bitboard`의 도입을 기각하고,
마인크래프트 서버 환경(`Zero-GC`, `JIT` 예열 한계)에 맞추어 자체적인 `Hybrid Pathfinding` 아키텍처를 채택합니다.
탐색 구조는 기하학적 대칭성에 따라 다음 세 가지로 분리됩니다.

1. `Leaper` 방식: 고정 오프셋 기반 탐색 (`Knight`, `King`)
2. `Slider` 방식: 방향성 벡터 기반 `Raycast` 탐색 (`Rook`, `Bishop`, `Queen`)
3. `Asymmetric` 방식: 이동/공격 판정 비대칭 전용 탐색 (`Pawn`)

### Rationale

마인크래프트 서버는 플레이어의 단일 클릭 시점에 단 한 번의 `Lazy Evaluation`만 수행하므로,
`Magic Bitboard` 도입은 명백한 오버엔지니어링입니다. 또한, '도약' 버프 등 동적 규칙 확장에 유연하지 못해 예외 연산 오버헤드가 발생하고,
낮은 호출 빈도로 인해 `JIT` 컴파일러 예열이 배제되어 런타임 인터프리터 부하와 메모리 점유 오버헤드만 유발하므로 도입을 배제합니다.
대신 기물별 탐색 알고리즘을 분리하여 구조화함으로써 연산 비용과 유지보수성을 최적화합니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**:
  이동 검증과 공격 검증 기능을 물리적으로 분리하여,
  `Queen`과 같은 슬라이더 기물의 8방향 `Raycast` 연산을 중복 실행하고 모든 탐색 알고리즘을 단일 `God Class`에 구현하는 설계를 기획했습니다.
* **Why it Failed**:
  탐색 시 발생하는 고비용 `Raycast` 연산의 중복 호출과 이에 따른 가비지 객체 할당 누적으로 인해
  `Tick` 지연이 발생할 위험성이 개발 및 코드 검토 단계에서 제기되어, `Hybrid Pathfinding` 구조로 분리하여 선제적으로 차단되었습니다.

### ADR-024: Explicit Optimization over JIT Reliance in Hot Path

### Decision

초당 수백, 수천 번 호출되는 `Hot Path`에서는 **`JIT` 컴파일러에 대한 맹신을 배제하고 명시적인 데이터 지향 코딩을 강제합니다.**

- 1회성 변수는 컴파일러를 믿고 방치하는 대신 명시적으로 인라인화하여 추상 구문 트리의 복잡도를 낮춥니다.
- 가독성을 위해 로직을 잘게 쪼개거나 래퍼 객체를 생성하는 행위를 금지하며, 원시 타입과 평탄화된 데이터 파이프라인을 유지합니다.

### Rationale

현대 `JVM`의 `JIT` 컴파일러는 인라인화나 죽은 코드 제거 등 강력한 런타임 최적화를 제공하며,
일반적인 환경에서는 개발자가 가독성 중심의 클린 코드를 작성하고 `JIT` 컴파일러에게 최적화를 맡기는 것이 정석입니다.
그러나 마인크래프트 서버의 한계를 방어해야 하는 `Hot Path` 환경에서는 이러한 `JIT` 컴파일러의 최적화 능력을 맹신할 수 없습니다.

이 결정은 두 가지 치명적인 런타임 위험을 원천 차단하기 위한 생존 전략입니다.

1. **`Warm-up` 랙 방지**: `Hot Path`의 `JIT` 컴파일러 최적화는 수만 번의 `Warm-up` 호출 이후에야 동작합니다.
   매치 초반 대규모 교전 시 인터프리터 모드로 동작하는 구간 동안 실시간 전투에서 발생하는 프레임 드랍과 랙을 유저들은 기다려주지 않습니다.
2. **최적화 포기 회피**: 메서드의 바이트코드가 길어지거나 스택 변수가 많아지면,
   `JIT` 컴파일러는 과부하를 막기 위해 해당 메서드의 **최적화를 아예 포기합니다.**

따라서 컴파일러의 자비에 서버 성능을 맡기는 대신, 처음부터 `JIT` 컴파일러가 최적화를 100% 수행할 수밖에 없도록,
그리고 예열 전에도 가볍게 돌아갈 수 있도록 **명시적으로 깎아낸 코드를 작성하는 것이 우리 아키텍처의 근간입니다.**

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**:
  일반적인 환경처럼 가독성 중심의 클린 코드를 작성하고 최적화를 전적으로 `JIT` 컴파일러에게 맡기는 정석적인 접근법을 시도했습니다.
* **Why it Failed**:
  매치 초반 인터프리터 모드로 동작하는 구간 동안 대규모 전투에서 심각한 프레임 드랍과 랙이 발생했으며,
  메서드의 바이트코드가 길어지면 `JIT` 컴파일러가 과부하를 막기 위해 최적화를 아예 포기하여
  `Tick` 지연이 영구히 해결되지 않는 치명적 런타임 위험이 발생했습니다.

### ADR-025: Command and Permission Isolation

### Decision

플레이어용 인게임 액션 명령어와 운영자용 관리 도구 명령어를 물리적으로 철저히 분리합니다.
바닐라 마인크래프트의 엔진 관리자 권한인 `isOp()` 상속을 방지하기 위해 게임 룰 관리자 권한은 플러그인 설정 시 기본값을 거부로 강제합니다.
또한, 서브커맨드별로 권한을 파편화하는 것을 금지하고 명령어 진입점 단위의 통일된 권한 검증 구조를 강제합니다.

### Rationale

게임 룰의 검증을 받는 정상적인 상태 전이와 룰을 무시하는 강력한 운영 도구는 목적과 생명주기가 완전히 다릅니다.
바닐라 마인크래프트의 엔진 권한과 플러그인 고유의 게임 로직 권한을 완벽히 분리함으로써 엔진 격리 원칙을 유지하고 `RBAC` 환경을 구축합니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**: 단일 명령어 핸들러 내부에서 `isOp()`로 권한을 체크하고 플레이어 동작과 디버그 동작을 섞어 구현했습니다.
* **Why it Failed**:
  다른 개발자가 새로운 서브커맨드를 추가할 때 권한 체크를 누락하여 관리자 도구가 일반 유저에게 노출되는 보안 공백이 발생했고,
  엔진 권한과 게임 권한이 강결합되었습니다.

### ADR-026: Visual Feedback Priority and Zero-GC Object Pooling

### Decision

디버그 및 UI 시각화를 위해 채팅창 도배를 유발하는 텍스트 출력을 배제하고, `BlockDisplay`를 활용한 `Show, Don't Tell` 원칙을 채택합니다.
`Hot Data`로 취급되는 인게임 시각화(예: 체스판 타일 등 잦은 상태 변이)는 매치 진입 시점에 객체 `Pool`을 구성하며,
상태 변이 시 엔티티를 `remove`하거나 `spawn`하는 대신 `BlockData`나 `Scale` 필드만을 갱신하는 `In-place Mutation` 방식을 사용합니다.
단, 명령어 호출 등에 의해 이산적으로 드물게 발생하는 `Warm/Cold Data` 시각화(예: 관리자용 벙커 뷰어)의 경우
무의미한 풀링 메모리 점유를 막기 위해 필요 시 `spawn`하고 소멸 시 `remove`하는 직관적 방식을 허용합니다.

### Rationale

순수 ECS 아키텍처와 달리 Java 기반의 Bukkit 엔진에서 엔티티를 껐다 켜기 위해 `spawn/remove` 패킷을 남발하는 것은
객체 할당, 청크 레지스트리 동기화, 네트워크 지연 등 최악의 `GC` 오버헤드를 유발합니다.
따라서 잦은 렌더링이 필요한 `Hot Data`는 이미 스폰된 엔티티를 영속적 캔버스로 취급하여 메타데이터만 갱신하는 것이 압도적으로 가볍습니다.
반면 갱신 빈도가 극히 낮은 `Cold Data`는 힙 공간 확보가 더 중요하므로 `spawn` 및 `remove`를 허용하여 메모리 누수를 방지합니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**: `Hot Data`인 인게임 시각화 상태 토글 시 `Presenter`가 기존 엔티티를 파괴하고 다시 소환하는 방식을 사용했습니다.
* **Why it Failed**:
  무거운 엔티티 생성 및 삭제 연산이 메인 틱 루프에 반복적으로 쌓이면서 막대한 가비지 지연 현상과
  대규모 상태 전환 서버 랙을 유발하는 치명적인 안티 패턴이 되었습니다.

### ADR-027: Flat Data Structure Priority for Tiny Collections

### Decision

크기가 5 미만인 극소형 컬렉션을 관리할 때,
논리적으로 요소의 중복 방지가 필요하더라도 `HashSet`의 사용을 금지하고 `ArrayList` 또는 원시 배열을 강제합니다.
중복 방지가 필요하다면 `contains()`를 통한 선형 탐색 연산을 감수합니다.

### Rationale

극소형 데이터의 경우 이론상 빠른 해시 탐색보다 선형 탐색이 `Hardware Prefetcher`의 캐시 히트 덕분에
실제 하드웨어 레벨에서 압도적으로 빠릅니다.
또한 `HashSet`은 요소 추가 시마다 노드 객체를 새로 할당하여 `GC`를 유발하고 힙을 파편화시키므로,
잦은 상태 변이가 일어나는 게임 루프 환경의 `Zero-GC` 철학에 정면으로 위배됩니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**: 관리자 뷰어 목록 등 중복 방지가 필요한 곳에 습관적으로 백엔드식의 `HashSet`을 도입했습니다.
* **Why it Failed**:
  데이터가 1~3개에 불과함에도, 켰다 껐다 할 때마다 무의미한 노드 가비지가 힙에 누적되고 포인터 간접 참조 오버헤드만 커졌습니다.

### ADR-028: Branchless Execution and Data-Driven Array

### Decision

진영(백/흑) 등 상호 배타적인 주체를 식별하여 데이터를 분리 관리할 때,
개별 필드로 나누거나 로직 내부에 식별용 분기문을 작성하는 것을 안티 패턴으로 간주하고 배제합니다.
대신 데이터를 배열 형태의 `Data-Driven` 구조로 설계하여,
조건문 없이 열거형 인덱스만으로 즉각 접근하는 `Branchless Execution`을 강제합니다.

### Rationale

조건문은 `Branch Prediction` 실패 시 CPU 파이프라인을 비우고 엄청난 사이클 낭비를 초래하는 주범입니다.
자바의 2차원 배열은 메모리 연속성 이점은 떨어지나, 최상단 배열 크기가 작아 무조건 L1 캐시에 상주하므로 간접 참조 오버헤드는 0에 수렴합니다.
식별용 분기문을 데이터 구조 접근으로 완전히 치환하여 얻는 CPU 파이프라인의 이득이 압도적으로 큽니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**:
  진영별 기물 목록을 분리된 두 개의 리스트로 선언하고, 모든 메서드마다 `if`문으로 흑/백을 나누어 로직을 `Copy & Paste` 했습니다.
* **Why it Failed**: 분기 예측 실패 패널티로 인한 CPU 낭비는 물론, 코드 중복이 극심해져 가독성과 유지보수성이 완전히 박살 났습니다.

### ADR-025: Multi-Entity State Management and AoS Preference

### Decision

다중 기물과 같은 거대 상태 데이터 군집을 관리할 때는 다음 원칙을 준수합니다.

1. **메모리 공간과 논리 소속의 분리**: `Composite Entity` 안에 다른 `Composite Entity`를 리스트로 넣는 중첩을 금지합니다. 다수의 기물 객체들은 `Manager` 내부의 독립적인 1차원 전역 배열 풀로 격리하여 배치하며, 상위 엔티티들은 오직 기물의 논리적 식별자만을 가집니다.
2. **참조 Desync 방지와 Pooling**: 다중 배열 크기를 동적으로 변경하는 것을 금지합니다. 세션 시작 시 배열을 최대치로 단 한 번 `Pooling`하며, 상태 갱신 시에는 껍데기 객체 내부 값만 덮어쓰는 `In-place Mutation` 방식을 사용하여 배열 참조 자체를 영구 불변하게 고정합니다.
3. **AoS 채택**: 데이터를 쪼개어 배열로 관리하는 `SoA`를 기각하고, 단일 기물이 모든 상태를 캡슐화하여 배열로 배치되는 `AoS`를 채택합니다.

### Rationale

배열 크기를 동적으로 재할당하면 여러 `Manager` 간에 메모리 주소가 끊어지는 치명적인 참조 `Desync`가 발생합니다. 사전 `Pooling`과 `In-place Mutation`을 통해 가비지 생성을 완벽히 차단하고 데이터 무결성을 방어할 수 있습니다.
또한 극단적 최적화를 위한 C++ 방식의 `SoA`는 힙 메모리에 포인터가 흩어지는 자바 환경에서는 캐시 히트율 상승이 0에 수렴합니다. 성능 이득 없이 인덱스 동기화 복잡도만 폭증하므로, 자바 생태계에서는 가독성과 객체지향 안정성을 챙길 수 있는 `AoS`가 압도적인 최적해입니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**: 상위 엔티티인 `Match` 객체 내부에 `Piece` 객체 배열을 직접 포함시켜 할당했습니다.
* **Why it Failed**: `Composite Entity`가 다른 `Composite Entity`를 품어버리면서 포인터 체이싱이 깊어지고 상호 참조 꼬임이 발생했습니다.
* **Failed Attempt**: C++의 데이터 지향 설계를 맹신하여 기물의 체력 배열, 공격력 배열을 따로 선언하여 관리하려 했습니다.
* **Why it Failed**: 자바에서는 원시 타입 배열이 아닌 이상 객체 배열은 캐시 히트율 개선에 전혀 도움이 되지 않아 성능 이득은 없고 로직만 극도로 복잡해졌습니다.

### ADR-026: External Identifier Mapping and LUT Pre-caching

### Decision

도메인 열거형 내부에 시각화 관련 외부 엔진 식별자를 필드로 하드코딩하거나 런타임에 문자열을 조작하여 매핑하는 것을 엄격히 금지합니다.
외부 식별자와의 매핑은 오직 시각화를 전담하는 `Presenter` 내부에서 서버 부팅 시점에 단 한 번 배열 형태의 룩업 테이블을 구축하여 런타임에 읽기 전용으로 활용해야 합니다. 

### Rationale

순수 게임 룰인 도메인 계층에 외부 플러그인의 식별자가 침투하면 의존성 역전 및 추상화 누수가 발생합니다. 
반대로 초고빈도로 실행되는 런타임 경로에서 도메인 열거형 이름을 외부 규격에 맞게 파싱하면 매번 새로운 `String` 객체가 할당되어 거대한 가비지 컬렉션 스파이크를 유발합니다.
따라서 `Presenter`가 초기화 시점에 2차원 배열에 식별자를 미리 채워 넣고 런타임에는 오직 배열 인덱스 접근만을 수행하여 문자열 조작 없이 캐시 히트를 달성하는 룩업 테이블 패턴이 결합도 최소화와 초고속 성능을 동시에 잡는 유일한 해답입니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**: 런타임에서 도메인 열거형의 이름을 외부 규격으로 변환하기 위해 유틸리티 클래스로 문자열 파싱 로직을 매번 호출했습니다.
* **Why it Failed**: 마인크래프트 게임 틱 내부에서 몬스터 갱신이 일어날 때마다 무의미한 문자열 분해조립 연산 비용과 메모리 쓰레기가 누적되어 심각한 프레임 드랍을 야기했습니다.

### ADR-027: Entity Immutability and Rejection of Domain Object Pooling

### Decision

게임 세션 단위의 거대 도메인 객체를 재사용하는 오브젝트 풀링 패턴을 엄격히 금지합니다.
기물의 근본 타입이나 제어 권한이 바뀌는 거대한 사건은 속성 갱신이 아니라 엔티티의 완전한 파괴 및 재창조로 처리하며, 껍데기 객체는 철저히 폐기하고 새로 할당해야 합니다.

### Rationale

마인크래프트 엔진 특성상 몹의 물리적 외형이나 제어 권한을 바꾸려면 기존 엔티티를 지우고 새로 소환해야 하므로 반드시 `Primary Key`가 변경됩니다. 식별자가 변경된다는 것은 기존 논리 객체의 사망을 뜻합니다. 
이는 곧 특정 식별자가 살아있는 동안에는 해당 기물의 뼈대 속성이 절대 변하지 않음을 수학적으로 증명합니다. 따라서 도메인 껍데기는 모든 불변 속성을 안고 있는 순수 `record`로 굳혀 포인터 체이싱을 차단해야 합니다.
수십 개의 껍데기 객체 할당을 아끼기 위해 식별자 불변성을 가변으로 뚫어버리는 오브젝트 풀링은, 찌꺼기 데이터 누수라는 치명적 버그를 낳을 뿐만 아니라 자바 힙의 에덴 영역 가비지 컬렉터에게는 최적화 이득조차 0에 수렴하는 극악의 오버엔지니어링입니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**: 메모리 최적화를 핑계로 매치 시작 시 텅 빈 기물 객체 배열을 미리 풀링해두고, 런타임에 내부의 식별자와 타입을 `Setter`로 덮어쓰려 시도했습니다.
* **Why it Failed**: 이전 기물의 쓰레기 데이터가 완벽히 초기화되지 않아 엉뚱한 유저에게 디버프가 전이되는 치명적인 상태 오염 버그가 발생했으며, 불변성 파괴로 인해 추적 불가능한 스파게티 코드가 되었습니다.

### ADR-028: JIT-Optimized Logging and Console UX Strategy

### Decision

게임 서버 콘솔 에러 로그는 단순히 데이터를 남기는 것을 넘어 관리자의 시선을 강제하는 강력한 시각적 장치로 취급합니다.
에러 렌더링 코드는 JIT 컴파일러의 메서드 인라이닝을 유도하기 위해 메인 루프에서 분리하여 격리하며, 여러 줄의 로그는 텍스트 블록을 사용하여 원자성을 확보합니다. 관리자용 내부 에러 메시지는 상수로 외부화하지 않고 예외 발생 지점 직전에 하드코딩하여 행위의 지역성을 극대화합니다.

### Rationale

초고빈도로 호출되는 틱 루프 내부에 거대한 문자열 에러 로깅 코드를 섞어두면 바이트코드가 비대해져 JVM이 최적화를 포기하게 됩니다. 에러를 출력하는 무거운 코드를 별도의 헬퍼 메서드로 격리하면 메인 로직의 바이트코드가 얇아져 극단적인 인라이닝을 달성할 수 있습니다.
또한 수많은 에러가 동시에 쏟아지는 서버 환경 특성상 여러 번의 로깅 호출은 텍스트 파편화를 유발하므로 텍스트 블록으로 단 한 번에 출력해야 합니다. 시선을 잡는 이모지와 빈 줄은 인지 부하를 줄이는 완벽한 콘솔 UX 설계이며, 디버깅 시 코드 점프를 막기 위해 내부 로깅 메시지는 상수 클래스가 아닌 호출부 근처에 직접 하드코딩하는 것이 최적입니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**: 메인 로직 내부에 여러 줄의 로깅 코드를 직접 나열하고, 메시지 내용은 엔터프라이즈 백엔드 관성에 따라 에러 코드 상수 클래스로 묶어 분리했습니다.
* **Why it Failed**: 메인 루프 메서드가 너무 커져 JIT 컴파일러가 인라이닝을 포기하여 TPS 저하가 발생했습니다. 또한 동시성 환경에서 에러 로그가 서로 뒤섞여 출처를 알 수 없게 되었고, 원문을 확인하려 상수 클래스를 오가느라 디버깅 피로도만 폭증했습니다.

### ADR-029: Fail-Fast Assertion and Blast Radius Isolation

### Decision

불가능한 논리적 상태에 대해서는 조용히 무시하지 않고 단언문을 사용하여 즉시 크래시를 유발하는 `Fail-Fast` 전략을 채택합니다. 반대로 기획적으로 이미 목적이 달성되었거나 외부 요인에 의해 대상이 증발한 경우에는 로그 스팸 없이 조용히 실행을 마치는 `Graceful Degradation` 패턴을 사용합니다.

### Rationale

마인크래프트 서버 아키텍처는 단언문 예외가 발생하더라도 해당 틱의 특정 이벤트만 중단될 뿐 서버 전체가 셧다운되지 않는 완벽한 `Isolation` 인프라를 갖추고 있습니다. 따라서 `Blast Radius`가 좁은 이 환경에서는, 불가능한 상태를 조용히 덮고 넘어가 추적 불가능한 스노우볼 버그를 유발하는 것보다, 에러 발생 즉시 요란하게 크래시를 내어 개발자가 버그 위치를 즉각 파악하도록 강제하는 것이 가장 안전한 방어막입니다. 
반면 몹이 물리 엔진에 의해 이미 소멸된 경우 등은 대상 삭제라는 목적이 이미 달성된 `Idempotency`를 지니므로, 에러 로그 없이 조용히 종료하는 것이 틱 루프를 보호하는 최적의 설계입니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**: 유효하지 않은 월드나 널 좌표가 들어왔을 때, 백엔드 관성에 따라 에러 로그만 남기고 조용히 리턴 처리했습니다.
* **Why it Failed**: 서버의 메인 상태는 다음 페이즈로 넘어갔으나 정작 텔레포트되지 않은 유저들이 로비에 갇히는 끔찍한 `Zombie State`가 발생했으며, 조용히 넘어간 탓에 최초 발생 원인을 추적할 수 없어 스파게티 버그가 되었습니다.

### ADR-030: Phase Transition Ordering and Zombie State Prevention

### Decision

게임 상태 머신에서 거대 상태 변이를 수행할 때는 반드시 사전 검증 로직을 우선해야 합니다. 특히 시스템 셋업을 동반하는 전역 페이즈 전환의 경우, 물리적 환경 준비와 시각적 데이터가 클라이언트에 100% 동기화된 직후에 최종적으로 상태를 갱신하고 브로드캐스팅해야 합니다.

### Rationale

상태 변수를 먼저 갱신한 후 도중에 조건 미달로 반환 처리할 경우, 시스템 메인 상태는 이미 다음 페이즈로 전환되었으나 부수 효과가 실행되지 않아 클라이언트와 서버 간 치명적인 불일치가 발생합니다. 이로 인해 유저가 기존 공간에 고립되는 `Zombie State`는 영구적으로 복구할 수 없으므로, 모든 물리적 검증과 환경 셋업이 통과된 직후에만 상태 갱신을 허용해야 데싱크를 원천 차단할 수 있습니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**: 특정 페이즈로 전환할 때 상태 변수를 가장 먼저 갱신한 후, 보드판 유무 등을 검사하여 조건 미달 시 예외 리턴 처리를 수행했습니다.
* **Why it Failed**: 검증 실패 시 부수 효과가 실행되지 않아 유저는 기존 월드에 고립되었으나, 시스템 상태는 이미 진행 중으로 갱신되어 게임 진행과 초기화가 모두 불가능해지는 `Zombie State`가 발생했습니다.

### ADR-031: Law of Mutability for Zero-GC Root Entities

### Decision

`Composite Entity` 내부 데이터를 평탄화하여 루트 객체에 고정할지, 별도의 가변 `Component`로 분리할지 결정하는 유일한 잣대는 가변성입니다. 시스템의 조회 빈도와 무관하게 런타임에 값이 변할 여지가 단 한 번이라도 존재한다면, 무조건 가변 컴포넌트 내부로 격리해야 합니다.

### Rationale

승급 시스템처럼 기물의 핵심 속성이나 식별자 자체가 바뀌는 거대 이벤트가 발생할 때, 속성이 불변 루트 객체에 평탄화되어 있으면 객체 전체를 파괴하고 다시 할당해야 하는 비용이 발생합니다. 가변성이 있는 속성들을 모두 컴포넌트로 격리하면, 상태 변이 발생 시 루트 객체의 재생성 없이 컴포넌트 내부 값만 수정하는 방식을 통해 객체 재할당을 멸종시키는 완벽한 파이프라인을 유지할 수 있습니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**: 메모리 히트율과 잦은 조회 빈도를 근거로 기물 타입이나 조종권 같은 가변 데이터를 루트 불변 객체에 직접 평탄화했습니다.
* **Why it Failed**: 기물이 승급할 때 기존 객체 내부의 값을 바꿀 수 없어 새로운 객체를 강제로 할당해야 했으며, 이로 인해 객체 재할당을 피하지 못하고 가비지 스파이크 방어선이 붕괴되었습니다.

### ADR-032: Synchronous Time-Slicing over Asynchronous Execution

### Decision

시각화, 텔레포트, 스폰 등 월드 환경을 조작하는 모든 물리적 작업은 비동기 스레드로 분리하는 것을 엄격히 금지합니다. 부하가 우려되는 거대 작업은 메인 스레드 환경에서 프레임 단위로 작업을 잘게 쪼개어 분산시키는 시간 분산 최적화 기법을 강제합니다.

### Rationale

월드 블록이나 엔티티를 비동기 스레드에서 조작할 경우 엔진 내부의 데이터 경합으로 인해 즉각적인 시스템 크래시가 발생합니다. 대규모 기물을 한 번에 소환하는 부하를 막고자 비동기 타이머를 도입하면 서버 셧다운 위험이 있으므로, 동기 스레드 안에서 1틱당 1개씩 순차적으로 분산 소환하는 방식만이 서버의 안전성과 부드러운 병렬 연출을 모두 보장하는 유일한 해법입니다.

### 🛑 Anti-Patterns & Past Failures

* **Failed Attempt**: 카운트다운 타이머와 대규모 기물 스폰이 겹칠 때 발생하는 틱 저하를 방지하기 위해 비동기 타이머를 활용하여 연출 로직을 분리했습니다.
* **Why it Failed**: 비동기 스레드에서 월드 공간에 접근하여 엔티티를 스폰하려 시도한 즉시 데이터 경합으로 인한 예외가 발생하여 게임 진행이 완전히 멈추는 치명적 크래시가 발생했습니다.
